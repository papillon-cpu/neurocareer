# NEUROCAREER — архитектура

## Стек MVP (версии проверены 30.10.2026)

- Next.js 16.4 (App Router), React 19, TypeScript, Tailwind CSS 4
- PostgreSQL + Drizzle ORM (у Prisma 8 в npm пока `rc`). Локально без установки Postgres работает встроенный PGlite (настоящий PostgreSQL в WASM), в проде — `DATABASE_URL`.
- Собственные сессии вместо Auth.js (см. ниже), Zod, Vitest; S3-хранилище и Playwright — позже

## Принципы

1. **Модульность.** `src/modules/<domain>` (assessments, matching, billing, ai, resume, consent) — бизнес-логика без UI и без прямых вызовов БД из компонентов.
2. **Название — конфиг.** Бренд хранится в `src/config/brand.ts`, смена названия — одно место.
3. **Деньги и лимиты — конфиг.** Тариф (1 000 ₽/мес, 50 контактов, 200 ₽ за доп. контакт) лежит в `src/config/pricing.ts` как значения по умолчанию; на этапе 8 переедут в `AdminSettings` в БД.
4. **Баллы считает код.** Проверка тестов — детерминированная; AI не меняет ключи и шкалы.
5. **AI Gateway.** Единая точка для Claude/GPT: таймауты, лимиты, валидация ответов по Zod, учёт стоимости, учёт согласий перед отправкой данных провайдеру.
6. **Приватность по умолчанию.** Контакты и результаты тестов отдаются работодателю только по отдельному согласию. Права проверяются на сервере при каждом действии.
7. **Честные интеграции.** Не настроено → явная ошибка/пометка, никаких фиктивных «успехов».

## Дизайн-система

Тёмная графитовая основа, акцент — кислотно-лаймовый («нейрон»), вторичный — холодный фиолетовый. Заголовки — Unbounded, текст — Onest (оба с кириллицей), моно — JetBrains Mono. Токены заданы в `src/app/globals.css` через `@theme`.

Компоненты: `src/components/ui` (Button, Card, Badge, Section), состояния загрузки/ошибки/пусто добавляются вместе с первыми реальными экранами данных (этап 3).

## Авторизация (этап 3)

- Пароли: scrypt (N=2^15) с солью, параметры хранятся рядом с хэшем. При входе неизвестного email выполняется фиктивная проверка, чтобы время ответа не выдавало существование аккаунта.
- Сессии: случайный токен 256 бит в httpOnly-cookie (sameSite=lax, secure в проде); в БД хранится только sha256 токена. Срок — 30 дней, выход удаляет сессию на сервере.
- Почему не Auth.js: Credentials-вход в Auth.js требует JWT-сессий без отзыва, а v5 остаётся beta. Собственный слой небольшой (~150 строк) и полностью покрыт тестами.
- Права проверяются на сервере в каждой странице и каждом серверном действии (`requireRole`); `proxy.ts` — лишь быстрая проверка наличия cookie. Роль администратора нельзя выбрать при регистрации: только `npm run db:seed`.
- Ограничение частоты (вход, регистрация) — в памяти процесса. При нескольких серверах заменить на общее хранилище.
- Cache Components выключены: кабинеты полностью динамические.

## Резюме (этап 4)

- Данные: `resumes` (контейнер) и `resume_versions` (версии: содержимое в jsonb, источник, пометки «проверьте»). Содержимое валидируется Zod при записи и при чтении.
- Импорт PDF/DOCX: тип определяется по содержимому файла (сигнатуры), не по имени; лимит 5 МБ и 10 страниц PDF; DOCX проверяется на наличие `word/document.xml`. Сам файл **не сохраняется**: хранится только извлечённый текст, чтобы пользователь мог сверить результат.
- Разбор текста — по правилам (`modules/resume/parser.ts`), без AI: ничего не додумывается, неопределённое остаётся пустым, импортированные данные всегда помечены «проверьте» до подтверждения пользователем. Качество разбора приблизительное; точный разбор с AI — этап 6 (потребует защиты от prompt injection и согласия на внешние AI).
- Права: каждая операция принимает `userId` и проверяет владельца через JOIN; чужие id дают 404. Лимиты: 10 резюме на пользователя, 20 версий в резюме.
- Экспорт в PDF: страница печати + диалог «Сохранить как PDF» браузера (кириллица и вёрстка без дополнительных библиотек). Серверная генерация PDF — при необходимости позже.

## Тестирование потенциала (этап 5)

- Определения тестов лежат в коде (`modules/assessments/definitions`) вместе с ключами проверки и баллами. Версионирование: у каждого определения есть `version`; попытка запоминает версию, с которой начата. Для обновления методики добавляется новая версия, а старая остаётся в реестре. Таблицы вопросов и вариантов в БД не нужны: так ключи никогда не попадают на клиент и не могут быть изменены через БД или AI.
- Прохождения хранятся в БД: `assessment_attempts` (версия, seed порядка заданий, статус), `assessment_answers` (уникальна пара «попытка — задание»), `assessment_results` (уникален по попытке; полный снимок отчёта, поэтому старые результаты не меняются при обновлении методики).
- Порядок заданий и вариантов перемешивается по seed попытки: при возобновлении порядок тот же. Одна незавершённая попытка на тест и пользователя гарантируется частичным уникальным индексом.
- Подсчёт — чистые функции (`engine.ts`) без AI и времени. Объективные задания: 1 балл за верный ответ. Ситуационные: сумма баллов выбранных вариантов по компетенциям, доля от максимума по направлению. Самооценка (шкала 1–5, есть обратные пункты) показывается отдельно и в основной балл не входит. Свободные ответы не оцениваются автоматически: после теста показывается рубрика для самопроверки.
- Честные границы: нет норм, процентилей и сравнения с другими людьми; если разброс между направлениями меньше 15 п.п., сильные стороны и зоны роста не выделяются; время прохождения не влияет на результат; везде указано, что это предварительная оценка, а не валидированный тест.
- Защита от «угадывания»: тест целостности проверяет, что в ситуационном задании нет варианта, лучшего по всем направлениям сразу. Числа в аналитических заданиях пересчитываются независимо в тестах.
- Завершение идемпотентно (повторный вызов возвращает сохранённый результат, результат создаётся один раз), нельзя завершить с пропусками, после завершения ответы менять нельзя. Результаты видит только владелец; передача работодателю — этап приватности.

## AI-шлюз (этап 6)

- Единая точка вызова `modules/ai/gateway.ts`; провайдеры Anthropic и OpenAI — официальные SDK, ключи только из серверного окружения (`config.ts`). Модель Claude по умолчанию `claude-sonnet-5-5` (переопределяется `ANTHROPIC_MODEL`); для OpenAI модель обязательна в окружении, в код она не зашита.
- Порядок проверок: ключи → **согласие пользователя на внешний AI** → лимит запросов в час → месячный лимит токенов → вызов. Без согласия данные провайдеру не уходят. Согласие хранится отдельной записью с версией текста и отзывается.
- Таймаут на задачу; повтор (1 раз) только при временных сбоях (таймаут, 429, 5xx); при постоянной ошибке (ключ, запрос) — переход к резервному провайдеру, если он настроен. Все текущие задачи — чтение без побочных эффектов, поэтому повторы безопасны. Пользователь видит понятную ошибку без технических деталей.
- Структурированные ответы проверяются Zod; при несоответствии — одна попытка исправления, затем ошибка. Непроверенный ответ дальше не передаётся.
- Журнал `ai_usage`: провайдер, модель, токены, задержка, статус; **без текста запросов и ответов**.
- Защита от выдумывания в резюме (`resume/guards.ts`): каждое значение из ответа AI сверяется с исходным текстом, чего там нет — удаляется; переформулировка с новыми числами отклоняется; AI-правки только предлагаются, применяет их пользователь. Ограничение: если «инструкция» из документа сама содержит нужные слова, сверка её пропустит. Поэтому результат всегда помечен «проверьте».
- Консультант (`modules/assistant`): в системную инструкцию не попадают имя, email и результаты тестов; данные профиля передаются в изолированном блоке с пометкой «это данные, не инструкции». Пара «вопрос — ответ» сохраняется только при успешном ответе.
- Что не проверено: реальные ответы моделей (ключей в разработке нет). Логика шлюза, ограничения и защиты покрыты тестами с подставными провайдерами.
- AI-пояснение к отчёту (`assessments/ai.ts`): по кнопке, только по расчётным показателям (без имени, контактов, свободных ответов, разбора заданий); результат хранится в `assessment_results.ai_commentary`, повторный показ не тратит запросы. Страховки: схема Zod, запрет диагнозов/IQ/выводов о пригодности, проценты в тексте обязаны совпадать с рассчитанными. Оплата 500 ₽ (этап 8) закроет всё это за общим доступом.

## Оплата и подписки (этап 8)

- **Деньги — в копейках** (целые). Тарифы хранятся в `admin_settings` и меняются администратором (`/admin/pricing`), по умолчанию: доступ сотрудника 500 ₽ разово; подписка 1 000 ₽ на 30 дней, 50 контактов, 200 ₽ за контакт сверх лимита. Изменение действует на новые платежи: купленный период хранит цену и лимиты на момент покупки.
- **Платёж оплачен только по подтверждённому событию провайдера.** Создание платежа и возврат пользователя на сайт доступа не дают. Единственное место смены статуса: `processPaymentEvent` (транзакция, блокировка платежа, уникальный `(provider, event_id)` → повторная доставка безопасна; сумма события должна совпасть; оплаченный платёж нельзя «провалить» поздним событием).
- **BillingProvider** (`modules/billing/provider.ts`): `createCheckout` и `verifyWebhook`. Реального провайдера для РФ в коде нет и он не имитируется: подключается реализацией интерфейса и записью в `getProvider()`. Webhook: `POST /api/billing/webhook/<provider>`, без верной подписи — 401.
- **Тестовый режим (sandbox)**: включается явно (`BILLING_PROVIDER=sandbox`) или по умолчанию вне production; везде помечен «Тестовый режим, деньги не списываются»; страница имитации оплаты существует только в нём. В production без провайдера оплата недоступна (а не «успешна»).
- **Доступ сотрудника** (`employee_access`): единая проверка `requireEmployeeAccess` в страницах и серверных действиях тестов, отчётов, резюме и консультанта. Профиль, приватность и главная бесплатны.
- **Подписка**: каждый оплаченный период — строка `subscriptions`; продление начинается после конца текущего периода (оплаченное время не теряется); автопродления нет. Неудачный платёж ничего не меняет. После окончания новые контакты закрыты.
- **Контакты**: `unlockContact` в транзакции с блокировкой строки подписки (`FOR UPDATE`) — параллельные запросы не превысят лимит. Первые N уникальных контактов периода — «включены»; повторное открытие в том же периоде ничего не списывает (уникальность `(subscription, candidate)`); сверх лимита контакт открывается только после подтверждённого платежа за него. Платёж, пришедший после окончания подписки, помечается `needsReview` (нужен ручной возврат), а не теряется молча.
- Ограничение проверки: тесты на встроенной БД выполняют транзакции по очереди, поэтому защита от гонок подтверждается логикой и блокировками, но не нагрузочным тестом на PostgreSQL. Доступность данных кандидата (видимость, согласие на публикацию) подключается на этапах 7 и 9: сервис контактов пока ведёт только учёт.

## Приватность и удаление данных (этап 9)

- **Закрыто по умолчанию.** `profile_visibility`: опубликован ли профиль, какая версия резюме показывается, какие контакты разрешены. Пока пользователь ничего не включил, работодатель не видит ничего.
- **Публикация** (`visibility/service.ts`) требует одновременно: отдельное согласие на публикацию (запись с версией текста), версию резюме, которую пользователь проверил (импорт с пометками «проверьте» не публикуется), заполненную специализацию и оплаченный доступ. Согласие и публикация пишутся одной транзакцией. Публикация действует, только пока действует согласие: отзыв согласия скрывает профиль, даже если флаг остался.
- **Что видит работодатель** (`getPublishedCard`): специализация, город, желаемая должность, формат, «О себе» и выбранное резюме без имени, email и телефона. **Контакты** (`getCandidateForEmployer`) выдаются, только если одновременно: профиль опубликован, работодатель открыл контакт в рамках подписки, кандидат дал отдельное согласие на передачу данных и выбрал, что показывать. Результаты тестов работодателю не передаются (флаг и согласие под них появятся с подбором).
- **Отзыв и скрытие** доступны всегда и не зависят от оплаты: «скрыть профиль» (согласие остаётся), «скрыть и отозвать согласие», «отозвать согласие на передачу данных» (контакты закрываются сразу).
- **Удаление аккаунта** (`deleteAccount`, для сотрудника и работодателя; подтверждение паролем и словом «УДАЛИТЬ»): удаляются профиль, резюме и версии, результаты тестов, диалоги с AI, публикационные настройки, компания работодателя, сессии. Строка пользователя остаётся обезличенной (email заменён, пароль непригоден, `deleted_at`), потому что платежи и подписки хранятся по требованиям учёта; записи о согласиях и журнал действий тоже остаются как подтверждение. Сроки хранения и формулировки должен утвердить юрист.
- **Журнал действий** (`/admin/audit`): регистрации, согласия и отзывы, публикация, платежи, смена тарифов, удаление. Содержимого профилей и сообщений в журнале нет.

## Вакансии и подбор кандидатов (этап 7)

- **Вакансии** (`modules/vacancies`): создание, правка, отправка на модерацию, отзыв, закрытие, повторное открытие. Всё, кроме закрытия и отзыва, требует действующей подписки (`getActiveSubscription`). Статусы: черновик → на модерации → опубликована / отклонена → закрыта. Править можно только черновик и отклонённую; «опубликована» ставит только администратор (`/admin/vacancies`, причина отклонения обязательна и видна работодателю; снять опубликованную тоже можно). До 30 незакрытых вакансий на работодателя. Любая операция принимает `employerId` и ищет вакансию по паре «id + владелец»: чужие id дают «не найдено».
- **Дискриминационные формулировки** (`matching/rules.ts`): простая проверка текста вакансии на пол, возраст, национальность, религию, здоровье, семейное положение, внешность. Находка блокирует отправку на модерацию и одобрение. Это страховка по регулярным выражениям, а не полный фильтр: окончательно решает модерация.
- **Разбор требований** (`vacancies/analyzer.ts`, «VacancyAnalyzerService»): AI-задача `vacancy_analysis` через `aiCompleteJson` (схема Zod, один повтор на исправление, текст вакансии в изолированном блоке `<vacancy>`). Согласие работодателя не нужно: в запросе только его собственный текст (`consent: "none"` в контексте шлюза). Навыки, которых нет в тексте вакансии, отбрасываются; ответы с недопустимыми формулировками скрываются. **Без AI** (не настроен, ошибка, невалидный ответ) показывается проверка по правилам с явной пометкой «AI не использовался». Разбор только предлагает: на подбор влияют навыки, внесённые самим работодателем.
- **Подбор** (`matching/service.ts`, «CandidateMatchingService»; без AI): (1) пул — `listPublishedCandidateIds`, содержимое только через `getPublishedCard`; (2) фильтр по обязательным навыкам (по умолчанию все; по флажку — хотя бы половина); (3) оценка 0–100 из навыков (55 обязательные, 20 желательные), стажа по датам резюме (15, если требуется) и формата работы (10): веса пересчитываются, если критерий не задан или данных нет, а отсутствие данных пишется в «ограничения данных»; (4) сортировка (оценка, закрытые обязательные навыки, id), топ-20 сохраняется в историю. Навыки ищутся по целым словам с синонимами (`matching/skills.ts`), стаж считается объединением интервалов (`matching/experience.ts`), непонятные даты не угадываются. Версия алгоритма хранится в рекомендации (`rules-1`). В расчёт попадают только навыки, стаж и формат: пол, возраст и прочее в алгоритм не входят, результаты тестов не читаются никогда.
- **Объяснение** (`score.ts`): «подтверждено данными» (где именно найден навык), «чего не хватает», «что можно развить», «ограничения данных». Оценка называется «совпадением с требованиями по данным профиля», не вероятностью найма; автоматических отказов нет.
- **Вывод AI по кандидату** (`explainWithAi`, задача `match_explain`): только по кнопке работодателя, отдельно от данных и без влияния на оценку и порядок. Нужны: AI настроен и **отдельное согласие кандидата `ai_matching`** (новая цель согласия, настраивается в `/me/privacy`). Шлюз проверяет согласие кандидата, а не работодателя (`AiContext.consent`). Провайдеру уходит карточка без имени и контактов; email и телефоны, вписанные кандидатом в текст, заменяются на «[скрыто]». Ответ проверяется схемой и запретом на вероятность найма, рекомендации отказать и признаки из списка выше.
- **История и аудит**: `match_recommendations` (оценка, число закрытых обязательных навыков, объяснение, версия алгоритма, вывод AI), без имён и контактов. Показ всегда сверяется с текущей публикацией: скрытый кандидат пропадает из выдачи сразу и не открывается по старой ссылке. Журнал: `vacancy.*`, `match.run`, `match.reported`, `contact.unlocked`, `contact.payment_started`. Удаление аккаунта кандидата стирает его рекомендации, работодателя — вакансии и рекомендации по ним.
- **Жалобы** (`recommendation_reports`): работодатель отправляет жалобу на рекомендацию (одна на рекомендацию), администратор видит в `/admin/reports` то, что было показано (оценку и объяснение), и закрывает с заметкой. Кандидат в жалобе не раскрывается.
- **Контакты**: страница кандидата доступна только по рекомендации из вакансии работодателя. До действия показывается стоимость (`quoteContact`): «входит в подписку, будет использован контакт N из 50» или «лимит исчерпан, 200 ₽, откроется после подтверждённой оплаты». Контакт нельзя открыть и оплатить, если кандидат не разрешил передачу данных (`contactsShareable`): списания не будет. Цена из формы сверяется с текущей. Показ контактов только через `getCandidateForEmployer`.
- **Ограничения**: пул ограничен 300 опубликованными профилями на запуск, а карточки читаются по одной; при росте базы нужен предвычисленный индекс или поиск на стороне БД. Словарь синонимов навыков короткий. Стаж считается общий, а не по роли. После оплаты контакта сверх лимита пользователь возвращается на страницу подписки, а не на карточку. Вывод AI на живых моделях не проверялся (ключей нет): проверены логика, схемы и защиты на подставных провайдерах.

## Главная по ролям и демо-переключатель

- `/` — выбор «Я развиваю карьеру» / «Я ищу сотрудников»; `/employees` и `/employers` — отдельные лендинги; регистрация по ссылке с ролью показывает анкету только для неё (`/register?role=...`).
- **Демо-переключатель** (`modules/demo`, `components/DemoSwitcher.tsx`) в шапке публичных страниц и кабинетов рядом с кнопкой темы: входит в заранее созданные демо-аккаунты (`demo-admin@`, `demo-employer@`, `demo-employee@example.com`) без пароля. Включён при разработке; в production только с `DEMO_MODE=1`, иначе действие отказывает. Не включайте на рабочем сайте: это вход в аккаунты без пароля.
